# Translate teaching materials

日本語で書いた学生向けの教科書（`docs/**/*.html`）を、学生の母国語に展開する。翻訳済みのHTMLはコミットしない。コミットするのは、文単位の対訳カタログ `i18n/<言語>/<ページ>.json` と用語集 `i18n/<言語>/glossary.md` だけで、各言語のHTMLはカタログから作る。

## 前提

- **授業は日本語で進む。** 翻訳は、読んで理解するための補助である。先生が口にする言葉、画面に出る言葉と、訳文の言葉を、学生が結び付けられるようにする。
- **日本語版が正。** 日本語の教科書（`docs/`）は、翻訳の都合で書き換えない。原文が曖昧で訳せないときは、推測で訳さず、PR本文に挙げる。
- **訳すのは、未翻訳の文だけ。** 日本語の文を直すと、その文は自動で未翻訳に戻る（古い訳は外れ、学生には日本語で表示される）。変わっていない文の訳は触らない。
- 言語の一覧は `config/i18n.json`、言語ごとの用語集は `i18n/<言語>/glossary.md` にある。
- この授業では、学生の使う道具が系統で変わり、**画面の表示言語も道具によって違う**。画面に出る言葉の扱い（下の「そのまま残すもの」）は、この表で決まる。

| 道具 | 使う単元 | 表示言語 | 訳文での扱い |
| --- | --- | --- | --- |
| Monaca クラウドIDE・ダッシュボード（Google Chrome 上） | Monaca系（M01〜） | **日本語** | 日本語のまま残し、訳をかっこで添える |
| Visual Studio Code | Flutter系（F01〜） | **英語** | 英語のまま残す |
| Xcode・Android Studio・iOSシミュレータ・Androidエミュレータ | Flutter系 | 英語 | 英語のまま残す |
| macOS（Finder など）・Google Chrome のメニュー | 全単元 | 学生ごとに違う | 原文の日本語を残し、訳をかっこで添える |

訳す先の言語と書き方は次のとおり。

| 学生の母国語 | コード | 書き方 |
| --- | --- | --- |
| 英語 | `en` | |
| 中国語 | `zh-Hans` | 簡体字 |
| 広東語 | `zh-Hant-HK` | 繁体字の書き言葉に、香港の語彙を使う（程式、檔案、螢幕）。話し言葉をそのまま書く粤語白話文にはしない |
| 韓国語 | `ko` | 下の「韓国語（`ko`）の注意」を読む |
| ミャンマー語 | `my` | Unicodeで書く（Zawgyiではない） |

## 手順

1. 未翻訳の文を書き出す。

   ```sh
   python3 scripts/localize-student-materials.py sync --lang en
   ```

   カタログが今の日本語に合わせて整理され（使わなくなった訳が外れる）、`dist/i18n-work/<言語>/<ページ>/todo-NNN.json` ができる（`dist/` はGit管理の対象外）。1ファイルは40文ほど。同じ文が複数のページにあるときは、最初のページの作業ファイルにだけ出る。1回訳せば、全ページに入る。ページを絞るときは `--page docs/hello-monaca/index.html` を付ける。
2. 訳す前に、そのページの日本語のHTML（`docs/…`）を通して読む。文だけを見ても、見出しなのか、ボタンの名前なのか、表のどの列なのかが分からない。作業ファイルの `where` は、その文がどの要素にあるかを示す（`h2`、`td`、`img alt` など）。
3. 作業ファイル1つにつき、`done_file` に書いてあるパスへ、訳を `id` と訳文の組だけのJSONで書く。原文は書かない。

   ```json
   {
     "0dce59d92673": "Three goals",
     "4e8d3eaf93d9": "Save the file and check the result in <strong>プレビュー</strong> (Preview)."
   }
   ```

   `previous_source` と `previous_translation` が付いている文は、日本語が少しだけ直された文である。ゼロから訳し直さず、前の訳を、変わった分だけ直す。
4. 検査する。落ちた訳は、理由が出るので直す。

   ```sh
   python3 scripts/localize-student-materials.py merge --lang en --dry-run dist/i18n-work/en/hello-monaca/index/done-001.json
   ```

   「検査に通った訳」が、そのファイルで訳した文の数と同じなら、全部通っている。「カタログに入る数」のほうが多いのは、同じ原文がほかのページにもあり、そこにも入るためである。
5. カタログへ入れる。`--dry-run` を外す。ファイルを省くと、その言語の `done-*.json` をすべて入れる。すでに訳がある文は入れ替えない（入れ替えるときは `--overwrite`。1文だけ直すなら、カタログの `translation` を直接直してよい）。
6. 確かめる。

   ```sh
   python3 scripts/localize-student-materials.py check
   python3 scripts/localize-student-materials.py status --lang en
   python3 scripts/localize-student-materials.py build --lang en
   ```

   `build` は `dist/i18n-preview/docs/<言語>/…` にページを作る。`file://` で開くとCSSが当たらないことがあるので、ローカルのサーバーで開く。レイアウトの崩れ、リンク、コードのコピー、共通資料の「もとの教科書へ戻る」を確かめる。コピーボタンと進捗表示は、配布物と同じ `config/i18n.json` の `languages[].ui` で出るので、本文の説明とボタンの文言が食い違っていないかもここで見る。

   確認用ページには、言語の切り替え（`language-nav`）と翻訳の注記（`translation-note`）は入らない。この2つは配布対象の全言語がそろって初めて作れるもので、`--lang` で選んだ言語だけを作る確認用ページではリンク先が欠けるため、配布時（`package-student-materials.py`）だけで付ける。
7. 新しく訳語を決めた用語を、`i18n/<言語>/glossary.md` に足す。

### 同じ原文を場所によって訳し分けるとき

既定は、`entries` の1つの訳を全ページで使う。**用語の表と表の見出しのように、役割が違うため同じ訳にできない文だけ**、そのページのカタログに `overrides` を足す。用語の表で日本語を残す決まりは変えない。

たとえば `i18n/en/hello-monaca/index.json` では、既定の `コード — code` を残したまま、表の見出しを `Code` にする。

```json
{
  "source": "docs/hello-monaca/index.html",
  "language": "en",
  "entries": [
    {"source": "コード", "translation": "コード — code"}
  ],
  "overrides": [
    {"source": "コード", "where": "th", "translation": "Code"}
  ]
}
```

- `source` は取り出した原文をそのまま使う。既存の `entries` または作業ファイルからコピーし、原文は書き換えない。
- `where` は、文を取り出した要素の名前（`th`、`td`、`p` など）。属性なら `img alt`、`nav aria-label` のように、要素名・半角スペース・属性名で書く。作業ファイルの `where` もこの形式である。文字を直接持たない要素はその子から取り出すため、`<th><strong>コード</strong></th>` のような形では `strong` になる。ページのHTMLも見て確かめる。
- 適用先は、**そのカタログのページ内にある、同じ `source` と `where` のすべての文**。同じSTEP内の `<th>コード</th>` と `<td>コード</td>` を分けられる。
- STEP番号・`id`・何番目の要素かは使わない。文や表を別のSTEPへ移動しても、原文と要素の種類が同じなら訳は保たれる。同じページ・同じ役割でも違う訳が必要な場合は、この指定では区別できないため、追加対応が必要な箇所として報告する。翻訳の都合で日本語の本文は変えない。
- `overrides` はそのページだけで使い、ほかのページの訳を補うときには使わない。`sync` と `merge` は有効な場所別の訳を残す。`merge --overwrite` も `entries` だけを入れ替える。場所別の訳を直すときは、該当する `overrides` の `translation` を直接直す。
- `check` は、同じ原文と場所の重複、指定の書式、タグや保護されたコード、現在の原文に対して存在しない `where` を検査する。原文が編集・削除された古い指定は、既定訳と同じく `status` の「使っていない訳」に数え、`sync` で外す。日本語を編集しただけではCIを落とさないため、原文の写し間違いも「使っていない訳」に出る。追加時はその数が増えていないことを確かめる。
- `status` の「訳した文」は、その原文が出るすべての場所に、既定訳か場所別の訳があるときに数える。一部の場所だけ訳してあれば未翻訳のままにする。

### 分担して訳すとき

ページごとにsubagentへ分けてよい。そのとき、次を守る。

- subagentは手順2〜4（`--dry-run` まで）を行う。**カタログへ入れる手順5は、親のセッションが1回で行う。** 同じカタログを同時に書き換えないためである。
- 用語集 `glossary.md` も、subagentには書き換えさせない。足したい用語は報告させ、親がまとめて足す。
- subagentには、このskill、用語集、日本語のページ、受け持つ作業ファイルのパスを渡す。

## 翻訳ルール（全言語に共通）

### そのまま残すもの

検査で強制するもの：

- `<code>`・`<kbd>` の中身。1文字も変えない。日本語が入っていても訳さない（`<code>/Users/ユーザ名/…</code>`、`<code>変数の名前</code>`）。
- `<pre>` の中のコードは、そもそも翻訳の対象にならない。訳文へ書き写さない。既知の技術との比較ブロック（`<div class="compare">`）のコードも `<pre>` の中なので同じ。
- `translate="no"` の付いた要素（比較ブロックの言語名ラベル `<p class="compare-lang" translate="no">JavaScript</p>` など）も、翻訳の対象にならない。
- `config/teaching-materials.json` の `terms` にある正式表記（いまは登録がない。基準のFlutter SDKの版の表記などを登録したら、その表記）。

検査はしないが、必ず守るもの：

- ファイル名、フォルダ名、パス（`config.xml`、`www/index.html`、`pubspec.yaml`、`lib/main.dart`）、パッケージ名（`f01_hello_flutter`、`package:flutter/material.dart`、`jp.ac.jec.…`）、クラス名、関数名、id、プロジェクト名（`M01HelloMonaca`、`F01HelloFlutter`）。
- **Flutterのウィジェット名、Dartのキーワード、パッケージ名。** `StatelessWidget`、`Scaffold`、`setState`、`async`、`final`、`shared_preferences` などは、原文で `<code>` に入っているので訳さない。原文が `<code>` に入れずに書いていても訳さず、PR本文に挙げる（日本語版を `<code>` に直すのは、翻訳PRではなく日常のPRで行う）。
- **Monaca クラウドIDEとダッシュボードの画面に出る言葉。** Monacaは日本語表示のまま使う（教科書のスクリーンショットも日本語の画面）。原文が日本語で書いているメニュー名・ボタン名・画面名は、どの言語でも日本語のまま残し、その言語での意味をかっこで添える。学生が画面の文字と見比べて探せるようにするためである。
  - クラウドIDEのメニュー：**ファイル**／**編集**／**表示**／**実行**／**ビルド**／**プロジェクト**／**設定**／**ヘルプ**
  - よく出る項目：**公開…**、**インポート**、**プレビュー**、**最小限のテンプレート**、**クラウドIDEで開く**、**新しいプロジェクトを作る**

  ```text
  原文：<strong>プロジェクト → 公開…</strong> を選びます。
  英語：Choose <strong>プロジェクト → 公開…</strong> (Project → Publish…).
  ```

  原文が画面の言葉を `<code>` で囲んでいる（AGENTS.md §12）ときは検査で守られるので、閉じタグのうしろにかっこ書きを添える（`<code>プロジェクト → 公開…</code> (Project → Publish…)`）。`<strong>` で囲んでいるときは検査で守られないので、中の日本語を訳してしまわないように気を付ける。かっこの訳は、用語集の「Monacaの画面に出る言葉」の表にそろえる。Monacaを英語表示にしたときの文字と同じとは限らない。学生が見るのは日本語の画面なので、意味が伝わればよい。
- **Visual Studio Code・Xcode・Android Studio・シミュレータ／エミュレータの画面に出る言葉。** どれも英語表示なので、原文が英語で書いているもの（**Open Folder…**、**Explorer**、**Command Palette**、**Run and Debug**、**Debug Console**）は、どの言語でも英語のまま残す。訳が要るときは、うしろにかっこで添える。原文がこれらの英語の画面名を日本語で書いていたら（「フォルダーを開く」など）、推測で英語に戻さずに訳し、PR本文に挙げる。
- **macOSとGoogle Chromeの画面に出る言葉。** 原文が日本語で書いているメニュー名やフォルダ名（**移動 → ホーム**、**書類**、**デベロッパーツール**）は、日本語のまま残し、その言語での名前をかっこで添える。学生のMacの表示言語は学生ごとに違い、ChromeのメニューもmacOSの表示言語に従うためである。

  ```text
  原文：Finderの <strong>移動 → ホーム</strong> を開き、
  英語：In Finder, open <strong>移動 → ホーム</strong> (Go → Home),
  ```

- **学生が打ち込む日本語と、画面に出る日本語。** 完成プロジェクトは日本語のままなので、訳文でも日本語のまま書き、意味をかっこで添える。全角スペースもそのまま残す。

  ```text
  原文：「テキストを変更」ボタンを押します。
  英語：Press the 「テキストを変更」 (Change text) button.
  ```

  意味を添えると、画面に出る別の文字と同じになって紛らわしいときは、言葉で説明する。
- **`<code>` の中の日本語の置き換え語を、本文で指すとき。** `<code>/Users/ユーザ名/…</code>` の `ユーザ名` のように、学生が自分のものに読み替える言葉は、本文でも日本語のまま書き、意味をかっこで添える（replace `ユーザ名` (user name) with your own）。
- **教科書自身のUI（コピーボタン、言語切替、進捗表示）は、この対象ではない。** ボタンのラベルは `config/i18n.json` の `languages[].ui` からその言語の文字が入るので、本文でもその言語のラベルをそのまま書く（`<strong>コピー</strong>` ではなく `<strong>Copy</strong>`／`<strong>复制</strong>`）。値は `ui` の `copy`・`copied`・`copy_shortcut` と完全に一致させる。
- **先生に質問するときの日本語の例文。** 「STEP 3の、setStateが分かりません」のように、学生が日本語で口にするための例文は、日本語のまま残し、意味をかっこで添える。授業は日本語で進むためである。

同じ言葉が、画面の表示名としても、ふつうの言葉としても出てくることがある。`左側の <strong>ダウンロード</strong> をクリック` はFinderの表示名なので `<strong>ダウンロード</strong> (Downloads)` と残し、`教材のファイルをダウンロードします` は動作なので download と訳す。Monacaでも同じで、`<strong>プレビュー</strong> を開く` は画面名なので残し、`変更をプレビューで確かめます` のような文の中のふつうの言葉は preview と訳す。`<strong>インポート</strong>`（ダッシュボードのボタン）と「完成プロジェクトを取り込みます」（動作）も同じように分ける。表示名に添えるかっこ書きは、同じページに何度出てきても、文ごとに毎回添える（文は1つずつ独立して使い回されるため）。

`img alt` も同じルールで訳す。ただし、画面に写っている日本語を全部残すと長くなるので、残すのは、その画像で学生が探すことになる言葉だけにする。

### タグと目印

- `<a1>…</a1>`、`<span2>…</span2>`、`<img3/>` は、属性つきのタグを番号で置き換えた目印である。原文にあるものを、同じ数だけ使う。語順に合わせて、並べる順番は変えてよい。
- `<strong>`、`<em>`、`<br>` などのタグも、原文と同じ数だけ使う。足さない。減らさない。
- 文字としての `<`、`>`、`&` は、`&lt;`、`&gt;`、`&amp;` と書く。原文にある `&amp;` などは、そのまま残す。
- 訳文の前後に空白や改行を入れない。

### 文体

- 読むのは、Monaca と Flutter の初学者である。ただし、プログラミングの入門者ではない。Web基礎（HTML / CSS / JavaScript）を履修し、Android（Java）と iOS（Swift）のネイティブアプリを作れる。短い文と、やさしい言葉で書く。1つの原文を2つの文に分けてよい。内容は足さない。引かない。
- **Web基礎・Android・iOS の用語は、学生が母語ですでに知っている定訳を使う。** 要素、属性、イベント、Activity、ViewController のような言葉を、言い換えたり説明を足したりしない。新しく覚えるのは、Monaca と Flutter / Dart の側の言葉（ウィジェット、状態、ホットリロードなど）だけである。
- 操作の手順は、その言語の手順書のふつうの言い方で書く（英語なら命令形：Click **Run**.）。
- **ふりがなは落とす。** 「実行（じっこう）できる」の「（じっこう）」は、日本語の読みを助けるためのもので、訳文には要らない。英語の言葉に添えたカタカナの読み（`Flutter（フラッター）`、`SDK（エスディーケー）`）も、元のつづりから読めるので落とす。
- **英語の表示に添えた日本語のかっこ書き**（`Name（名前）`、`<strong>Open</strong>（開く）`）は、訳すと同じ言葉の繰り返しになるなら落とす（英語で `Name (name)` とは書かない）。`Bundle Identifier（アプリを区別する名前）` のように説明になっているものは、訳して残す。
- **用語の表の用語は、日本語を残して訳を添える。** 「この単元で出てくるFlutterの言葉」のように、言葉とその意味を並べた表の「言葉」の列は、`宣言的UI — declarative UI` のように、原文のうしろに「 — 」と訳を書く。先生が授業で口にする言葉を、学生が聞き取れるようにするためである。用語が英字そのもの（`Flutter`）や、`<code>` の中のコード（`setState`）のときは、訳を足さない。
- **本文で用語を定義する文も、日本語を添える。** 「この書き方を<strong>宣言的UI</strong>といいます」は `This style is called <strong>declarative UI</strong> (宣言的UI).` のように、訳語のうしろへ日本語をかっこで添える。カタカナの用語（ウィジェット、メソッド）は、英語から読めるので添えなくてよい。
- かぎかっこ「」は、その言語の引用符にする。どの引用符を使うかは、用語集の「書き方の決まり」に書く。ただし、上の「画面やアプリに出る日本語」を囲むときは、「」のまま残してよい。
- 全角の記号（：（）、。）は、その言語の記号にする。`→`、`①②③`、`STEP 01` はそのまま残す。
- 単元の名前（`M01：HelloMonaca`、`F01：HelloFlutter`）は訳さない。「共通：はじめの準備」のような共通資料の名前は訳す。

### 韓国語（`ko`）の注意

- **文体は합니다体にそろえる。** 教科書なので、해요体・반말は使わない。手順の指示も「`Run`을 클릭합니다.」のように書く。
- **助詞は、直前に実際に読む音で選ぶ。** 英語やコードのうしろに助詞が来るときは、その語を韓国語で読んだときの終声で決める（`Flutter를`、`Monaca를`、`Run을`、`main 함수를`）。迷う語は用語集に「この語のうしろは을／를 のどちらか」を書き足す。日本語のまま残した画面の言葉（`<strong>プレビュー</strong>`）のうしろも、その日本語を読んだ音で選ぶ。
- 「이(가)」「을(를)」のようなかっこ書きの両論併記はしない。どちらかに決めて書く。
- **分かち書き（띄어쓰기）を守る。** 外来語とコードのあいだにも半角スペースを入れる（`Dart 파일`、`main 함수`）。
- 引用符は `'…'`（1文字・短い語）と `"…"`（文）を使い分け、用語集の「書き方の決まり」に書いたとおりにそろえる。「」をそのまま残すのは、上のルールにある「画面やアプリに出る日本語」を囲むときだけ。
- **漢字は使わない。** 日本語の漢字語をそのまま漢字で書かず、ハングルで書く（`変数` → `변수`）。ただし、原文の日本語を残す決まりのある箇所（用語の表、画面に出る日本語）では、日本語のまま残す。
- 英語由来の用語は、韓国の開発現場で通じる表記にそろえる（`프로젝트`、`패키지`、`함수`、`변수`、`빌드`、`에뮬레이터`、`시뮬레이터`、`위젯`）。決めた表記は必ず `i18n/ko/glossary.md` に書く。

### 一貫性

- 用語集 `i18n/<言語>/glossary.md` の訳語と「書き方の決まり」（引用符、見出しの大文字と小文字、チェック欄の文の形など）を使う。
- **同じ学生が、同じ学期に Kotlin演習（[jec-25cm-kotlin](https://github.com/LeoAndo/jec-25cm-kotlin)）も受けている。** 用語集の「両科目に共通の用語」（プロジェクト、変数、関数、実行、エミュレータなど）は、jec-25cm-kotlin の `i18n/<言語>/glossary.md` と同じ訳語にしてある。科目ごとに訳語が違うと、同じ言葉が別のものに見えて学生が迷う。この表の訳語を変えるときは、jec-25cm-kotlin の用語集も同じように直すissueを立てる。共通の用語を新しく足したときも、jec-25cm-kotlin に同じ語があればその訳語にそろえる。
- **ほかのページの見出しを引用している文**（リンクの文字「共通：はじめの準備」など）は、そのページのカタログにある見出しの訳と同じにする。まだ訳されていなければ、訳した言い方を報告し、あとで照合する。
- 同じ原文には、既定の同じ訳が入る（`merge` が、その原文を持つ全ページへ入れる）。役割が違う場所だけ、`overrides` で例外を指定する。

## 逆翻訳による照合

訳したのとは**別のsubagent（できれば別のモデル）**が、カタログの `source` と `translation` を並べて読み、意味の違い・訳し落とし・足しすぎ・操作順の入れ替わり・用語集との不一致を挙げる。

- 教員側で読めない言語（`my`、`ko`、`zh-Hant-HK`）では、**訳文を日本語へ訳し戻して**原文と比べる。訳し戻しは、原文を見ずに行う（原文を見ながらだと、訳文が足りなくても原文に引きずられて補ってしまう）。
- 照合したページと、見つけた違い、直した内容をPR本文に残す。担当（どのsubagent・どのモデルが訳し、どれが照合したか）も書く。
- 見つけた誤訳は、カタログの `translation` を直接直す。**`source` は手で書き換えない**（原文と合わなくなり、その訳が使われなくなる）。
- 全体を訳し直す必要はない。今回訳した文だけを照合する。

## `distribute` を `true` にする条件

`config/i18n.json` の `languages[].distribute` が `true` の言語だけが、学生用ZIPに入る。**初期値は全言語 `false`**（翻訳が1文もないため）。次のすべてを満たした言語から、1言語ずつ `true` に上げる。

1. `python3 scripts/localize-student-materials.py status --lang <言語> --require-complete` が通る（その言語の未翻訳が0）。
2. `python3 scripts/localize-student-materials.py check` が通る。
3. 上の「逆翻訳による照合」を終え、指摘をすべて反映してある。
4. `build --lang <言語>` で作った確認用ページを開き、レイアウト・リンク・コードのコピー・共通資料からの戻り先を目で確かめてある。
5. `i18n/<言語>/glossary.md` に、その言語で決めた訳語と書き方の決まりが書いてある。

`true` に上げるのは、上げる理由と確認結果を書いたPRで行う。**翻訳が途中の言語を `true` にしない。** `release-student-materials.py` の公開ゲートが、`distribute: true` の言語に未翻訳があると公開を止める。未翻訳を許可する `ALLOW_UNTRANSLATED` は緊急修正のための入力で、通常の配布準備では使わない。

## 配布前の差分翻訳

日常のPRの翻訳は不要。配布準備を依頼されたら、次の順で進める。

1. 最新のmainと配布準備のissueを確認する。`config/i18n.json` の `distribute: true` の言語を対象に、`status` で言語・ページごとの未翻訳を記録する。`distribute: false` の言語を、今回の配布のためだけに全文翻訳する必要はない。
2. 対象言語ごとに `sync --lang <言語>` を実行し、上の手順で未翻訳の文だけを訳す。新しい単元と、既存ページのサイドバーに増えた文も対象になる。前回の訳が残っている文を好みで書き換えない。
3. `area:i18n`、`size:*`、`enhancement` を付けた翻訳PRを開く。まだ学生用ZIPに入らない言語だけのPRには `skip-release-notes` も付ける。PR本文に配布対象の版、言語、変更前後の未翻訳件数を書く。**このPRを開いてから公開が終わるまでは、`docs/` を触るPRをマージしない。**
4. 上の「逆翻訳による照合」を行い、結果をPR本文に残す。
5. 最新のmainを取り込み、`check` と `status --require-complete` を実行する。未翻訳が増えたときは `sync` から差分だけをやり直す。対訳カタログの検査、AGENTS.md の検証コマンド、配布ZIPの入口 `index.html` から各言語の表示・リンクを確認する。
6. 翻訳PRをマージし、READMEの「手動公開」へ進む。公開自体は、オーナーから任されている場合に限る。Actionsは翻訳せず、対訳カタログから生成・検査するだけ。

## 翻訳PRのレビュー

- `check` が通っていること。未翻訳の数は `status` で見る。
- 分担して訳したときは、担当どうしで言い回しが割れていないかを見る（引用符、同じ見出しの訳、チェック欄の文の形、韓国語なら文体と助詞）。
- 逆翻訳による照合が行われ、担当と照合範囲がPR本文に書いてあること。
- 見つけた誤訳は、カタログの `translation` を直接直す。`source` は手で書き換えない。

## やってはいけないこと

- `docs/` の日本語を、翻訳の都合で書き換える。
- カタログの `source` を手で書き換える。並べ替えも `sync` と `merge` に任せる。
- `<pre>` や `<code>` の中身を訳す。
- 各言語のHTML（`dist/i18n-preview/` の中身、`docs/<言語>/`）をコミットする。
- 変わっていない文の訳を、好みで書き直す。差分が増え、レビューできなくなる。
- 翻訳が途中の言語の `distribute` を `true` にする。
