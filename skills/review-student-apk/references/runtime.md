# 動作と実行エラーの確認

提出されたFlutter APKをAndroidエミュレータに入れて確認する。iOSでの実行や、教材ソースを再ビルドした結果を提出APKの証拠にしない。静的収集だけの依頼ではこの手順を実行しない。

## 準備と対象の取り違え防止

`AGENTS.md` §7の「打ち切りの上限と引き継ぎ」「オーナーの作業を止めない」に従う。準備開始時刻を記録し、**準備・調整・待機の累計10分、同じ原因の再試行2回（初回込み3回）の先に届いた方で打ち切る**。同じ操作を無変更で繰り返さず、APKや画面を替えても数え直さない。ビルド・検査の時間とは分ける。端末を扱えない環境では準備せず、未確認の操作・期待表示・次の最小の操作・試したことを教員へ伝える。

1. `adb devices` で起動中の端末を調べ、候補ごとに `adb -s <シリアル> emu avd name` でAVD名とシリアルを照合する。他科目のAVD名を固定して使わず、実機は対象にしない。既存端末の利用了承がセッション内にあれば聞き直さない。了承がなければ、AGENTS §7の該当規則を示して利用可否を確認し、その間は静的収集を進める。
2. 既存端末を使えない場合、自分で起動する端末は `emulator -list-avds` の実在名から選ぶ。`-no-window -no-snapshot-save -port <空いている偶数ポート>` を使い、起動後にもAVD名とシリアルを照合する。IDEを起動せず、`adb kill-server`・`adb start-server` を実行しない。adbが応答しなければ再起動で直そうとせず引き継ぐ。
3. APKのManifestから**実際の**applicationIdと起動Activityを確認する。F02の作品でもF01のapplicationIdを持ち得るため、教材既定値をそのまま使わない。以下の `APK_REVIEW_*` は確認した値を設定する。`PACKAGE` と `COMPONENT` は正規のAndroid名で、シェル演算子等がないことを確認する。
4. `adb -s "$APK_REVIEW_SERIAL" shell pm path "$APK_REVIEW_PACKAGE"` で既存アプリを調べる。コマンド自体の失敗を「既存アプリなし」と判断しない。存在すれば、誰のどのアプリか、必要な記録と上書き・削除・データ消去の可否を確かめる。**無条件の `install -r`・`uninstall`・`pm clear` は使わない。** 同じapplicationIdの作品は直列で確認し、以前の保存値を今回の作品の初期状態にしない。既存アプリを復元できると仮定しない。

## 提出APKとログを対応させる

今回の出力ディレクトリにAPKのSHA-256、AVD名、シリアル、API・ABI、利用許可の確認結果、初期状態を記録する。再試行のファイルは前の試行を上書きしない。以下は1回分の例。

```sh
adb -s "$APK_REVIEW_SERIAL" shell getprop ro.build.version.sdk
adb -s "$APK_REVIEW_SERIAL" shell getprop ro.product.cpu.abilist
adb -s "$APK_REVIEW_SERIAL" install "$APK_REVIEW_APK"
```

コマンドの出力を保存し、インストールの `Success` を確認する。失敗時は署名不一致・minSdk・ABI・testOnly・破損・split APK不足などを切り分け、アプリのクラッシュとは記録しない。条件を確認せずインストールオプションを足して再試行しない。

起動前から `main`・`system`・`crash` のログを集める。クラッシュ後にPIDが消えたり変わったりするため、収集時点ではPIDだけで絞らない。既存ログの消去（`logcat -c`）は不要。端末時刻を使い、Macとの時差で試行範囲を取り違えない。

```sh
adb -s "$APK_REVIEW_SERIAL" shell "date '+%m-%d %H:%M:%S.000'"
adb -s "$APK_REVIEW_SERIAL" logcat -b main -b system -b crash -v threadtime -T 1 \
  > "$APK_REVIEW_OUTPUT/runtime-01.log" 2> "$APK_REVIEW_OUTPUT/logcat-01.stderr" &
APK_REVIEW_LOG_PID=$!
adb -s "$APK_REVIEW_SERIAL" shell am start -W -n "$APK_REVIEW_COMPONENT"
```

開始時刻と起動コマンドの出力も保存する。収集プロセスの存続とstderrを確認してから操作する。`-T 1` の直前1件は、開始時刻より前なら今回の結果に含めない。バックグラウンド収集を維持できない環境では、起動前の端末時刻を指定して `logcat -b main -b system -b crash -d -v threadtime -T '<端末の開始時刻>'` で取得し、バッファの循環による欠落の可能性を記録する。

必要な画面だけ、既存のUI操作ツールか `adb -s ... shell input` で操作する。ランダム操作だけで評価しない。入力は架空のローカルデータを使い、外部への投稿・課金・実在の個人情報を伴う操作をしない。通信がある作品では接続状態も記録する。画面が根拠になる場合は次のように保存する。

```sh
adb -s "$APK_REVIEW_SERIAL" exec-out screencap -p > "$APK_REVIEW_OUTPUT/screen-01.png"
```

## 比較版の完成確認から操作を選ぶ

以下は現在の教材に沿った候補であり、実際の比較版の教科書・教員ガイドの完成確認を先に読む。起動成功だけで全機能を確認済みにしない。

| 対象 | 操作と期待する結果 |
| --- | --- |
| F01・F02 | 初期画面の題材・名前・理由・色を確認する。入力済みデータはAPKに入らないため、新規状態で見える変更を区別する。 |
| F01・F02 | スタンプを押す・1つ戻す・0と上限を試し、回数・マーク・合計・ボタン状態が合うことを確認する。 |
| F01・F02 | 選んだ習慣の詳細に名前・理由・回数が出て、戻ると一覧の状態が維持される。 |
| F01 | アプリの終了・再起動で回数が0へ戻る。永続保存しないのが教材の仕様。 |
| F02 | 空欄は追加されず、正常入力は保存後に一覧・詳細に出る。入力画面を取り消した場合は追加されない。 |
| F02 | 保存した習慣と回数が、アプリの終了・再起動後に復元される。ホームへ移るだけの確認と区別する。 |
| F02 | 初期化を取り消すと記録が残る。確定の確認が必要なら評価用データで行い、初期データへ戻ることを確認する。 |

再起動のため `am force-stop` を使う場合も、今回の評価対象だと確認したパッケージとシリアルに限定する。記録を残すべき既存アプリを初期化しない。初期化・保存不正データの注入・通信失敗を一律に強制する試験にはせず、今回の変更や観測した問題に必要な操作を選ぶ。未実施の項目は理由とともに未確認にする。

## Flutter・Androidの実行エラーを分ける

**Javaの `FATAL EXCEPTION` がないこと、プロセスが残っていることだけでは正常と判定しない。** Flutterのフレームワークが捕捉するエラーや未処理Dart例外で、プロセスが残る場合がある。操作後の画面と値、Flutterログ、Androidログを照合する。

| 種類 | 根拠と判断 |
| --- | --- |
| Flutterフレームワークのエラー | `flutter` のログ・スタックと操作を対応付ける。build・layout・paintなどの失敗を、プロセスの終了と分ける。 |
| 未処理Dart例外 | `Unhandled Exception` 等の記録を読み、async処理の続きと再現操作を確認する。タグや文字列の有無だけで網羅したとしない。 |
| releaseのエラー表示 | 標準のbuildエラー表示はreleaseでは灰色になる場合がある。灰色画面だけで原因を断定せず、ログ・時刻・操作を合わせる。カスタムのエラー表示もあり得る。 |
| Android例外 | 対象プロセスの `FATAL EXCEPTION` と全スタック、入れ子の `Caused by` を読む。Android側の埋め込み・プラグインの関連箇所を確認する。 |
| native crash | signal・backtrace・対象プロセスを確認する。シンボル不足なら特定できる範囲を明記する。 |
| ANR | 応答停止の記録と操作を対応付ける。Java例外の不在を正常の根拠にしない。 |
| 通信・保存・入力の失敗 | クラッシュと区別し、期待するエラー表示や復旧操作も確認する。F02の標準教材には通信を含めない。 |

対象は今回の実行時間帯と、起動・終了ログ、applicationId、PIDで照合する。`:service` 等の別プロセスは対象アプリへの所属を確かめてから含める。別アプリの例外を混ぜない。ログが取れない、途中で切れた、画面を確認できない場合は、その範囲を未確認とする。

教員用レポートへ、APK SHA-256、比較commit、AVD/API/ABI、入力と初期状態、操作順、期待結果、観測結果、再現回数、ログ・画面の根拠を残す。「クラッシュ」「プロセスが終了しない実行エラー」「環境準備失敗」を区別し、症状だけで原因を確定しない。

## スタックと修正候補

- **Dartの難読化スタック**は、そのAPKと同じビルド・ABIに対応するsymbolsがある場合に `flutter symbolize -i <スタックのファイル> -d <対応するsymbols>` で確認する。別ビルド・別ABIのsymbolsを流用しない。symbolsの復元結果も元ソース全文ではない。
- **AndroidのJava/Kotlin側のR8難読化**には、そのビルドの `mapping.txt` とR8 retraceを使う。Dart symbolsと交換可能なものではなく、`mapping.txt` でDart AOT本体を復元しない。
- **native backtrace**も別に扱い、必要なシンボルがなければ原因箇所の特定に限界があると記す。
- ログのDart・Javaの行番号は「そのログに出た位置」とする。手元の教材や逆コンパイル結果の同じ番号と対応するとは限らない。`Unknown Source` や難読化名から元ソースの行番号を作らない。
- 元Dartソースやsymbolsが必要なら、どの再現操作・スタックの確認に必要かを説明する。なくても再現操作、観測エラー、確認する処理の候補は報告できる。例外名だけで修正コードを決めない。
- 修正を試していなければ「修正候補」と書く。エラーがなければ「実施した操作では観測しなかった」と範囲を添える。未確認の操作を含めて「問題なし」としない。

## 後片付けと引き継ぎ

終了時刻を保存し、自分で開始したログ収集プロセスだけを止める。例外終了時にもこの後片付けを行う。

```sh
adb -s "$APK_REVIEW_SERIAL" shell "date '+%m-%d %H:%M:%S.000'"
kill "$APK_REVIEW_LOG_PID"
wait "$APK_REVIEW_LOG_PID"
```

停止に伴う `wait` の非0終了をAPKの失敗にしない。必要な記録を保存してから、今回自分が入れた評価用アプリだけを片付ける。自分で起動したエミュレータだけを `adb -s <シリアル> emu kill` で終了し、オーナーの端末は終了しない。adbサーバーを止めない。

画面・ログ・個別講評は今回のローカル出力先に留め、受領APKは元の保管場所のまま変更しない。どちらもGitHubへ載せず、返却文には必要な対象アプリの事実だけを書く。終了した収集プロセス・アプリ・端末、残したものと理由を教員用レポートへ記録する。打ち切り時は未確認の項目、次の最小の操作、期待する表示、失敗原因と試行を伝える。
