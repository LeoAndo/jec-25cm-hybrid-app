# 教科書のFigmaデザインをコードへ反映する

このリポジトリの `AGENTS.md` と、`README.md` の「教科書のデザインをFigmaから反映する（教員用）」を先に読む。作業単位・並行作業・コミット・レビュー・配布の規則はそちらに従い、このスキルで別の規則を作らない。

## 正とする情報と作業範囲

- 見た目はFigma、教材の文章・学習順序・掲載コード・Monaca・Flutterの完成プロジェクトはGitを正とする。
- デザインの決定者・作業者はLeo Ando一人。別のデザイナーへの依頼や承認待ちを通常の工程に加えない。
- 「教科書全体へ反映」の依頼には、各単元へ共通するCSS・フォント・必要な資産の変更を含む。その範囲で共通変数を直すたびに再確認を求めない。
- 全単元のFigmaページを用意することは前提にしない。M01の共通デザインを適用し、M01にない構造は既存HTMLを保って確認する。F01/F02の差分コード・比較ブロックも対象に含める。新しい見た目を設計する必要がある場合だけ、その部分のデザインを決める。
- このスキルの通常の入力は、修正済みのFigma。コード反映の依頼だけでFigmaの値を変更しない。デザイン修正も依頼された場合は、該当Figmaスキルで編集・確認してから反映の参照版を確定する。
- 本文変更、学習上の意味、未知の操作仕様、Figma内部の矛盾、依頼範囲外への拡張が必要な場合に限り確認する。回答に依存しない作業は進める。

## 1. 対象と今回の参照点を確定する

1. 指定のissue・PRがあれば読み、再開時は同じ作業を引き継ぐ。新規作業のissue、専用worktree、重複着手・共有ファイルの確認は `AGENTS.md` に従う。別issueを扱ったセッションでは、新しいセッションを提案する。
2. ノードURL、反映対象（例：色と書体だけ／レイアウトも含む）、対象言語、除外範囲を既存の依頼から整理する。不足する場合は `README.md` の既定参照先を使う。
3. 新規作業は最新の `origin/main` を起点とし、SHAを記録する。既存PRの再開では作業ブランチを使い、最新mainとの差分と未マージの変更を確認する。ローカルのmainチェックアウトは変更しない。
4. 参照するFigmaの版名・版IDが取得できれば記録する。取得できない場合は、取得日時（タイムゾーン付き）、ノードID、変数・スタイルの取得値を記録し、固定された版を取得できたとは書かない。
5. Figma取得後に対象デザインを追加編集する場合は、その変更を今回へ含めるか次回へ送るかを決める。途中の版を混ぜない。

## 2. Figmaから最新の値と見た目を取得する

1. 利用可能な `figma-design-to-code` スキルを読み、Figma MCPの `get_design_context` を対象ノードに対して実行する。現在のツールスキーマに従い、HTML/CSSの実装であることを指定する。`skillNames` などの必須指定はそのスキルに従う。
2. スクリーンショットも取得する。長いページで応答が不完全な場合は、対象の見出し・本文・コード・表・確認欄などの子ノードに分けて取得する。
3. 変数・テキストスタイル・実際のノードへの関連付けを取得する。変数は参照先の基本色と有効なモードまで解決する。通常はライトモードだが、毎回確認する。
4. 変数名、ID、意味、解決後の値、関連付いたノードを確認する。表示名や過去のIDだけを根拠に機械的に対応付けない。ローカルの前回取得結果だけで今回の値を決めない。
5. 取得用に `use_figma` が必要なら `figma-use` を読み、読み取りに限定する。接続・権限・取得不全があれば原因を報告し、未取得値を画像から推測して実装しない。

現在の参照先とCSSの対応は [対応付けの注意](references/design-map.md) を読む。これは調査の出発点であり、最新デザインの代わりにはしない。

## 3. 差分と影響範囲を整理する

次の表を作り、Figmaと現在の有効なCSSを比較する。最新mainにも差分がなく、未マージの対象変更もない場合だけ変更不要と報告し、空の実装PRを作らない。その場合に既に作った自分の作業目印があれば `AGENTS.md` に従って片付ける。既存PRの変更によってFigmaと一致している場合は、追加編集不要としてそのPRの検証・レビューを続ける。

| Figmaの用途・変数 | 解決後の値 | 現在のCSS・セレクター | 反映先 | 影響するページ・状態 |
| --- | --- | --- | --- | --- |
| 取得した名前・ID | 今回の値 | 既存の値と適用規則 | 変更する規則 | 単元・言語・印刷など |

- `docs/assets/textbook.css` の `:root` と `.textbook`、後続の上書き、media query、言語指定を区別する。ファイル冒頭の値だけで実効値を判断しない。
- 対象の単元一覧は `config/teaching-materials.json` から得る。`rg` で対象変数、セレクター、共有CSSの参照、ページ固有のstyleを検索する。M01だけに専用の上書きを作らない。
- 「教科書全体」の共通デザインは各単元の `.textbook` に反映する。共有フォントなどの変更が共通資料・教員用ガイドにも届く場合は副作用を確認する。それらをM01と同じレイアウトへ全面変更することまでは含めない。
- 同じ色でも用途が違えば別の変数として扱う。CSS構文名が衝突する場合は用途別に分ける。全ファイルの同じhex値を一括置換しない。
- Figmaにしかない変数は、今回のデザイン変更の対象で、実装に必要と確認したものだけを適切なスコープに定義し、対象規則から参照する。対応表のブラウザ標準チェックボックスの参考値は、Figmaにあるという理由だけでCSSへ追加しない。変数の宣言を追加しただけで反映済みとしない。
- 依頼されていない既存差分は一覧に分ける。「色だけ」の反映で余白・本文まで変更しない。

## 4. 既存のHTML/CSSへ反映する

1. 編集直前に `AGENTS.md` の最新化・重複確認を行い、影響範囲に必要なファイルだけを変更する。
2. 既存の共有CSS・構造・資産を再利用する。Figmaの生成HTMLで教科書全体を置き換えない。本文全体をFigmaの絶対座標や固定ページ高で再現せず、既存の通常フロー、Flex、Grid、最大幅を使う。アイコンの重ね合わせなど、用途に適した既存の配置は保つ。
3. 目次・現在STEP・進捗・チェック欄・折りたたみ・リンク・読み上げ・キーボード操作の構造とJS接続を保つ。取り込み済みFigmaの改行やテキストレイヤー分割を本文へ移植しない。
4. RTLではCSSの論理プロパティを使い、本文の方向とコードのLTRを保つ。`pre.diff` の `ins`・`del`・省略行、比較ブロックを失わない。`data-check`・進捗キー・共通資料からの戻り先・言語切替を維持する。通常のデザイン反映では翻訳カタログを変更しない。
5. 色・不透明度、書体・太さ、文字サイズ・行高・字間、幅・余白・枠線・角丸など、今回の対象となる設計値を忠実に反映する。
6. 小数を一律に整数化しない。`16.2px`、`1.5px` の枠線、`line-height: 1.85` など意図した値を保持する。`29.600000381469727` は、元の指定値・計算関係から表現誤差と確認できる場合に `29.6` へ整理する。一律の小数桁数制限は設けない。
7. 相対値・計算式の意味を保つ。例えば本文18pxの `.9em` は16.2px、行高1.85は33.3pxだが、取得結果が小数だからという理由で固定pxへ変更しない。Figmaが特定用途の固定値を指定した場合は、その意図に合わせる。
8. フォント変更ではファミリー名だけでなく、実フォント・太さ・必要な文字を確認する。Figmaのスタイル名だけで太さを判断せず、解決後の数値を使う。可変フォントの600・750・800などを通常のMedium/Boldへ置換しない。
9. 新しいフォントは再配布条件を確認し、必要なファイル・ライセンス・取得元を `docs/assets/fonts/` に同梱して `@font-face` を更新する。CDN依存を追加せず、本文・コード内の日本語・言語別フォールバックを保つ。未対応の文字を別書体に置き換える必要がある場合は不足を示す。
10. 画像が対象なら元の資産とFigmaの書き出し資産を照合し、必要な実資産だけを採用する。比較用スクリーンショットを教材画像の代わりにしない。

## 5. 設計値と表示を確認する

[検証の選び方](references/verification.md) に従って、変更との関係がある代表箇所を選ぶ。

1. `AGENTS.md` 所定の教材検査・スクリプトテスト・翻訳抽出検査・配布ZIP生成を行う。新規の配布対象ファイルはパス指定でstageしてからZIPを生成する。
2. M01の変更箇所を同じ言語・表示状態・幅で比較する。現在のPC基準は1440 CSS px、ズーム100%。ブラウザ版、DPR、フォント読込完了も記録する。
3. 対象変数の計算後の値を確認し、画像では配置・折り返し・字形・読みやすさを確認する。他単元は同じ保証を繰り返さず、M01にない構造や別のCSS規則が当たる代表箇所を加える。
4. PCの画面分割幅でも、本文が欠けず、コードや広い表が枠内でスクロールできることを確認する。新しいモバイル用デザインの作成は既定にしない。
5. 共有フォント・全体の文字サイズなどを変えた場合は、言語別書体、印刷、展開したZIPのオフライン表示への影響も確認する。
6. 設計値が一致した後の文字のアンチエイリアス等の差を、画像全体の画素一致のためだけに補正しない。文字切れ・重なり・想定外フォールバック・ページ全体の横はみ出し・操作不能は解消する。同じ条件で折り返しが違う場合は、まず実装漏れを調べる。
7. 原因のない余白調整、本文への手動改行追加、段落ごとの微小座標補正、ページ全高を固定する修正で画像差分を隠さない。残る差は理由を記録する。

## 6. PRへ記録し、次回へつなぐ

- 最初のコミット後のDraft PR作成、push前の最新化、本文の構成、レビュー対応、マージ後の片付けは `AGENTS.md` に従う。
- Draftを外す前に対象Figmaを再取得し、今回対象の値・関連付けが参照時点と同じか確認する。変わっていれば差分を示して今回の対象へ含めるか確定し、必要な検証を更新する。更新日時が変わっただけで対象外の変更まで取り込まない。
- PRには、FigmaノードURL、参照版または取得日時、実装SHA、反映した用途・値・CSS対応、対象範囲、表示条件、実施した検証と未確認事項を記録する。
- `README.md` の参照先・フォント・運用方針が変わる場合は同じPRで更新する。恒久的な方針をエージェント固有の記憶へ保存しない。
- 比較画像・取得データは `AGENTS.md` 指定の検証用フォルダへ置き、通常はGitへ追加しない。次回に必要な判断と対応関係はPR本文・README・この対応表に残し、ローカルの検証画像だけを唯一の根拠にしない。
- マージ・学生向け公開は依頼と `AGENTS.md` の権限に従う。自動同期や自動公開が実装されたとは報告しない。Figma編集、コード反映、配布ZIP更新・公開を区別する。
- 次回は、その時点の最新Figmaと最新mainを再比較する。前回から変更がある範囲だけを反映し、新規の反映issueは新しいセッションで扱う。同じ未完了issueの再開では既存PRを使う。

## 完了報告

反映した内容、影響する教材、FigmaとPRへのリンク、確認した表示条件・検査結果、未確認事項、公開の状態を簡潔に報告する。部分確認を全体の実表示確認と表現しない。
